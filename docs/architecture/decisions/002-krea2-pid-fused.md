# ADR 002 — Krea2 → PiD Fused Upscaler (1024×576 → 4096×2304)

*Status: Accepted — single-queue fused profile `krea2-pid` (aliases `krea2_upscaler`, `krea2-upscaler`) alongside `krea2`/`krea2-1920x1080` and `pid`/`upscaler`. Primary bucket 1024×576→4096×2304, low-memory bucket 512×288→2048×1152.*
*Scope: TPU v5e-8 (`v5litepod-8`, 8 chips, `model` mesh `(8,)`) · BF16 diffusion, F32 Flux VAE (CPU), `pixel_space` passthrough · 6 artifacts, no new dependencies.*
*Spec: Extends `docs/architecture/proposed/003-pid-upscaler-bf16-support.md` (Phase A standalone PiD) to Phase B fused `krea2→pid` without host PIL round-trip.*

---

## 1. Context

`krea2` (Qwen3-VL-4B + WanVAE, 25 GB) and standalone `pid` (PiD + Gemma2-2B + Flux VAE + `pixel_space`, 1024×576→4096×2304 `×4` 4-step `lcm`/`simple`/`cfg1`) are supported separately. Users requested one workflow where a 16:9 image with 1024 as max side is generated by Krea2 and immediately upscaled by PiD — no `LoadImage`/`SaveImage` host round-trip, single queue item, 16:9 preserved.

Constraints:
- `v5e-8` has 16 GB HBM per chip, ~8.2 GB free after both diffusions resident. PiD 4096×2304 program alone reserves **9.03 GB** at bottom of memory (XLA HLO). With Krea2 (25 GB sharded → ~3.1 GB/chip) resident, free drops to **8.18 GB** → `RESOURCE_EXHAUSTED` at `SamplerCustom` `node 25` `sample_lcm` → `PixDiT_T2I._forward` `mark_step` (`comfy/ldm/pixeldit/model.py:233`).
- Krea 1024×576 and PiD 4096×2304 each fit standalone; fused needs ordering and/or smaller bucket.

---

## 2. Decision

Add a fused profile that reuses the 6 already-pinned artifacts, introduces two tiny execution barriers, and validates a single graph that decodes Krea via `qwen_image_vae` on CPU, forwards the `IMAGE` tensor to `flux1_vae` encode, and decodes PiD via `pixel_space`.

### 2.1 Profile & constants (`comfy/tpu_profile.py:16`)

- New profile `krea2-pid` with aliases `krea2_upscaler`, `krea2-upscaler` (`SUPPORTED_PROFILES`).
- Constants `KREA_PID_KREA_WIDTH=1024`, `KREA_PID_KREA_HEIGHT=576`, `KREA_PID_PID_WIDTH=4096`, `KREA_PID_PID_HEIGHT=2304`, `PID_UPSCALE_FACTOR=4`, `KREA_PID_SAVE_PREFIX=krea2-pid` (`PiD` also accepted). Second bucket `512×288→2048×1152` allowed for low-memory single-queue execution on v5e-8.
- Helpers `is_valid_pid_size` now allows `4096×2304` or `2048×1152` step16, `is_valid_krea_pid_size(krea_w,krea_h,pid_w,pid_h)` validates both buckets and `pid==krea*4`.
- `KREA_PID_SAVE_PREFIX_ALT=PiD` accepted.

### 2.2 Sharding & memory (`comfy/tpu_sharding.py:17`, `comfy/ldm/pixeldit/model.py:141`)

- `POLICY_VERSION` bump `krea2-pid-tpu-v1` → `krea2-pid-tpu-v2` (fingerprint includes new bucket).
- `pixel_mlp_chunks` default `2` → `8` (`PixDiT_T2I`) to reduce PiD pixel-stage peak (no quality change, chunked MLP).
- Existing `_PID_RULES` (239 sharded) + `_GEMMA2B_RULES` + `_FLUX_VAE_RULES` reused; `pixel_space` virtual replicated.

### 2.3 CLI & fingerprint (`comfy/cli_args.py:119`, `comfy/xla_backend.py:108`)

- `--tpu-profile` choices add `krea2-pid`, `krea2_upscaler`, `krea2-upscaler`.
- Fingerprint `latent=1024×576→4096×2304` (or `512×288→2048×1152` for small bucket) `tokens=krea 512:34:5+pixeldit 300` (`_cache_fingerprint_path`, `write_cache_profile`).

### 2.4 Warmup (`main.py:534`)

- `run_tpu_warmup` selects `Krea2-PiD-tpu.json` when profile is `krea2-pid` family, otherwise `Upscaler-tpu.json` / `Krea2-turbo-tpu.json`.

### 2.5 Execution barriers (`comfy_extras/nodes_tpu_flush.py:1`, `nodes.py:2545`)

New `comfy_extras/nodes_tpu_flush.py` (registered in `nodes.py:2545`):
- `TPUFlush` (`TPU Flush (fused Krea->PiD)`, `utils`, `IMAGE→IMAGE`): `wait_device_ops`, `free_memory(1e30, xla:0)` (frees 2 models), `unload_all_models`, `soft_empty_cache`, `wait_device_ops`, `metrics.clear_all`, logs `current_loaded_models` (3→1 before `AutoencodingEngine`+`PiD` reload). No-op on CPU.
- `TPUBridge` (`TPU Bridge (delay model load)`, `MODEL+IMAGE→MODEL`): passthrough `MODEL`; creates execution dependency `UNETLoader(pid) → TPUBridge ← TPUFlush` so PiD weights are not loaded until after Krea `VAEDecode`+`TPUFlush`. Without it both `UNETLoader`s run at graph start and PiD program sees Krea resident.

Both nodes are `ALLOW` in `tpu_profile` (not in `_UNSUPPORTED_*`), light validation only.

## 3. Alternatives Considered

- **No barrier, both models resident:** rejected — `RESOURCE_EXHAUSTED 9.03G > 8.18G` at `mark_step` even after `pixel_mlp_chunks=8`; HBM holds both programs (Krea 1024×576 + PiD 4096×2304) plus weights.
- **Evict XLA program cache via `_XLAC`:** no public `clear` (`torch_xla._XLAC` not importable, `runtime` only `initialize_cache`/`get_num_cached_compilation_graph`); `metrics.clear_all` insufficient.
- **Shard PiD more aggressively:** tiny norms/biases are the only replicated; large matmuls already sharded (%8). Further sharding would not reclaim 0.85 GB.
- **2× PiD model (not existent) or smaller Krea (512) only:** 512→2048 is the working single-queue alternative; 1024→4096 remains as two-queue manual (generate 1024×576 via `krea2` profile, then upscale that PNG via `pid` profile) which is already supported and operator-documented.

---

## 4. Consequences

**Positive:**
- Single-queue `krea2-pid` validates upstream only, reuses 6 artifacts, no new dependencies, no host PIL.
- `TPUFlush`+`TPUBridge` make PiD load after Krea decode, reducing peak `current_loaded_models` `4→3→1→3` and ensuring PiD program sees Krea weights not resident (Krea program still resident — see below).
- `512×288→2048×1152` fits v5e-8 single-queue; `1024×576→4096×2304` remains available as two-queue or on larger slice.

**Constraints accepted:**
- `1024×576→4096×2304` single-queue still OOMs on `v5e-8` due to **both XLA programs resident** (Krea program not evicted by `unload_all_models`/`free_memory`; `pixel_mlp_chunks=8` does not reduce 9.03G). Free stays `8.18G` vs `9.03G` needed. Requires either larger HBM slice or explicit two-queue execution (operator guide).
- Sampler/scheduler/CFG/batch/save-prefix remain frozen; only the two buckets above are allowed.

## 6. Follow-ups

- Add an explicit XLA program-cache eviction (e.g., `torch_xla` `clear_computation_cache` when available) or split `krea2-pid` into two queued prompts under one UI action for `1024→4096` on v5e-8.
- Consider `z-image-turbo` (12 GB diffusion vs 25 GB Krea) as alternative low-HBM Krea source already staged at `/kaggle/input/models/helltester2/z-image-turbo-bf16/transformers/default/1/models` (not yet profiled).
